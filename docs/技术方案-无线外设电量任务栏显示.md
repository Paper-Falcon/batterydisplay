# 无线外设电量 · Windows 任务栏常驻显示

技术方案 v0.2 · 2026-11-21 · 状态：待评审，未开始编码
（v0.2 变更：设备清单已确认，全部为国产 2.4G dongle，主线从"罗技 HID++"改为"2.4G 私有 HID 协议 + 声明式设备包"）

---

## 0. 结论先行

**能做，而且比 v0.1 评估的更容易——但容易的地方和我原先猜的不一样。**

三条硬结论：

1. **Windows 没有统一的无线外设电量 API。** 你这四台设备全部走 2.4G 私有接收器，标准协议一个都用不上（罗技 HID++、标准 GATT 全部无关）。数据只能从**接收器的厂商自定义 HID 接口**里问出来。
2. **Windows 11 移除了 DeskBand**，没有公开的任务栏插件接口。想真的显示在底边，只能"把窗口挂到任务栏上"。
3. **好消息：这类国产 dongle 的协议已经被社区摸透了方法论，而且你的鼠标有已知协议。** 真正的工作量不是"破解协议"，而是"把破解流程工具化 + 做一个好用的 UI"。

因此核心设计原则调整为一句话：**协议用声明式配置描述，不写死在代码里**。适配一个新品牌 = 写一个 JSON 文件，不改代码、不重新编译。这是这个项目能否长期维护的分水岭。

### 1.1 实测记录：ATK 蜻蜓 A9 Plus（已通过）

**结论：不需要逆向，社区已验证的帧直接可用。** 全流程 10 分钟内完成。

接收器在本机枚举为 6 个 HID 接口（产品名 `NK mouse NANO dongle`）：

| interface | usage_page | usage | 类型 |
|---|---|---|---|
| 0 | `0x0001` | `0x0002` | 鼠标 |
| 1 | `0xFFB3` | `0x0001` | 厂商（发帧无回包） |
| 2 | `0x0001` | `0x0006` | 键盘 |
| 2 | `0x000C` | `0x0001` | 消费者控制 |
| 2 | `0xFFB1` | `0x0001` | 厂商（发帧无回包） |
| 2 | **`0xFF05`** | `0x0001` | **厂商 — 电量在这里** |

收发记录（`interface 2 / usage_page 0xFF05`）：

```
请求  08 7D 72 02 00 01 07 01
回包  08 72 00 05 00 07 01 3A 70 0F 00 00 …
                          ↑  ↑─────↑
                        58%   3952 mV
```

- 第 7 字节 `0x3A` = **58%**
- 第 8–9 字节 `70 0F` 小端 = `0x0F70` = **3952 mV**，与 58% 互相印证
- 连续采样 4 次，数值完全一致

**踩到的两个坑（写进设备包，避免以后重犯）：**

1. **Feature Report 不可用**。`HidD_GetFeature` 在这个接口上直接 read error，必须走 `write` + `read` 的中断传输（`io: "output_input"`）。
2. **query 的第一个字节 `08` 是 Report ID**，必须原样发送，不能被引擎当成 payload 吃掉。

设备包已固化在 `device-packs/atk-a9-plus.json`。

> 剩余待办：与 ATK HUB 界面显示的电量做一次交叉核对，确认 58% 与官方读数一致（目前只有电压这一路旁证）。

### 1.2 实测记录：重力星球键盘（部分线索）

**先纠一个误判**：2.4G 键盘接上后枚举到的是 `3554:FA09`（厂商标识 `CX`），一度以为是狼蛛。但狼蛛官方 `config.xml` 明确写着两种模式都用 `0C45`，而当时两个 `0C45` 都不在线——所以这台是另一把键盘（重力星球）。**教训：不要靠"插拔前后什么变了"推断设备身份，要拿厂商配置做交叉验证。**

接收器 `3554:FA09` 的 7 个接口：

| interface | usage_page | 类型 |
|---|---|---|
| 0 | `0x0001`/`0x0006` | 键盘 |
| 1 | `0x0001`/`0x0080`、`0x0006`、`0x0002` | 键盘/鼠标 |
| 1 | `0x000C`/`0x0001` | 消费者控制 |
| 1 | **`0xFF02`**/`0x0002` | **厂商 — 可读** |
| 1 | `0xFF04`/`0x0002` | 厂商 — 只写，读取报 read error |

**`0xFF02` 上收到的一帧（连接建立时触发）：**

```
13 0A 01 00 04 02 00 00 00 00 00 00 00 00 00 00 00 00 00 24
                                                    ↑ 校验位
```

- **校验已破解：末字节 = 前面所有字节之和的低 8 位。**
  验证：`0x13+0x0A+0x01+0x00+0x04+0x02 = 0x24` ✓
  即 `checksum: { "mode": "sum_all", "at": 19 }`
- 该帧在第 4 字节 = `0x04`，可能是电量档位（0–4 级）或模式标识，**尚不能确认**

**已排除的路径：**

| 路径 | 结果 |
|---|---|
| 被动监听 `0xFF02` 25 秒 | 无任何推送 → 固件不周期上报 |
| 只读 Feature Report（report id 0x13） | read error → 接口不支持 Feature |
| `0xFF04` 读取 | read error → 只写通道 |

**结论：必须主动查询，协议未知，需要抓官方驱动的包。**

### 1.3 驱动里的线索（狼蛛）

官方驱动在本机 `D:\AULA F108Pro 三模机械键盘\`，是**原生 MFC 程序**（1.7 MB exe + `mui.dll` 1.1 MB），不是 Electron，没有明文 JS 可读。

但 `config.xml` 直接给出了答案：

<mode value="2" desc="2.4G TYPE-A" vid="0C45" pid="FEFE" product_name="2.4G Dongle"

- 有线：`0C45:800A`（Sonix 松翰方案），接口 `MI_00`
- 2.4G：`0C45:FEFE`，接口 **`MI_03`**

> ⚠️ **但实测与配置不符**：真机上狼蛛的 2.4G 接收器枚举为 `05AC:024F`「F108Pro Dongle」，不是 `0C45:FEFE`。说明官方驱动这一版配置对应的是另一个 SKU/批次。**教训：厂商配置只能当线索，必须以实机枚举为准。**

`mui.dll` 的导出符号里有两个关键类，说明驱动拿到的就是我们要的东西：

**下一步**：把狼蛛切到 2.4G，届时会出现 `0C45:FEFE`，直接按 `MI_03` 接口发帧试探（或用 `mui.dll` 静态分析定位命令常量）。

### 1.4 耳机：大概率无解

`4C4A:4155`「ZhuAudio ZG2」，厂商标识 `Jieli Technology`（杰理）——我之前猜的杰理方案，猜中了。

但**它只暴露 1 个 HID 接口（消费控制 `0x000C`），没有厂商自定义通道**。而杰理方案的私有 TLV 协议（参考 `3654:6901` 那类）需要 vendor 接口才能走。

### 1.5 关键发现：两个键盘是同一套 ODM 固件

狼蛛实机接收器 `05AC:024F`「F108Pro Dongle」有 9 个接口：

| interface | usage_page / usage | 类型 |
|---|---|---|
| 0 | `0x0001`/`0x0006` | 键盘 |
| 1 | `0x0001`/`0x0002` | 鼠标 |
| 2 | `0x0001`/`0x0080`、`0x0006`、`0x000E`、`0x000C` | 键盘/多媒体 |
| 2 | `0xFFFF`/`0x0001` | 厂商通道 |
| 3 | **`0xFF60`/`0x0061`** | 厂商通道（QMK Raw HID 签名） |
| 4 | **`0xFF60`/`0x0061`** | 厂商通道 |

三条通道都不主动推送（各监听 5 秒无数据）、都不支持 Feature Report。主动发帧后收到的回应：

```
if3  →  01 00 00 … 00 01        (0x01 = 0x01 ✓)
if4  →  0F 01 01 11             (0F+01+01 = 0x11 ✓)
if4  →  0F 01 FE 0E             (0F+01+FE = 0x10E → 0x0E ✓)
```

再对比重力星球那一帧：

```
0xFF02 → 13 0A 01 00 04 02 … 24  (13+0A+01+04+02 = 0x24 ✓)
```

**四帧全部满足"末字节 = 前面所有字节之和"。两个不同品牌、不同 VID 的键盘，用的是同一套帧格式（首字节为类型/命令码 + 求和校验）。**

这个结论的价值：

- 它们出自同一家方案商/同一套键盘固件 SDK
- **破解其中一把，另一把大概率直接能吃**，工作量减半
- 后续适配任何用这套 SDK 的国产键盘，都是同一个引擎

已知 `if3` 对 `0x01` 的回应是带回校验的回显，说明它不是 QMK/VIA 协议（VIA 的 `0x01` 应返回协议版本），而是 SDK 自己的命令集——**命令字必须从厂商驱动里取，不能猜**。

### 1.6 尚未验证的兜底：蓝牙模式

两个键盘都是三模，蓝牙模式下大概率暴露标准 GATT Battery Service（`0x180F` / `0x2A19`）。若成立，键盘电量就不用逆向 2.4G 私有协议了——代价是键盘要常连蓝牙而非 2.4G（键盘对延迟不敏感，代价可接受；鼠标则不可接受）。

探测脚本已就绪：`tools/probe/probe_ble.py`（基于 bleak）。切换键盘到蓝牙模式后执行：

```
python tools/probe/probe_ble.py --name F108
```

这条路径**零逆向、零风险**，值得在动抓包工具之前先试。

### 1.7 狼蛛 F108 Pro 打通（SONiX 协议）

**没有抓包，也没有逆向。** 社区已有完整实现：`donglover69/sonix-keyboard-studio`（对原生 MFC 驱动做过 Ghidra 逆向）明确记录了 2.4G dongle 的协议：

> MI_03、usage page FF60、**33 字节 output report**：report ID 0 + 命令字节 + **末字节为字节和校验**。
> 电量（两台都验证过）：请求 `20 01`，回包 `20 01 00 LEVEL …`，LEVEL 为百分比。
> 键盘只在 2.4G 模式下应答；该模式下它的 USB 命令接口会消失（线只能充电）。

实测（`if3` / `0xFF60`）：

```
发送  00 20 01 00 00 … 00 21        （33 字节，末字节 0x21 = 前面之和）
回包  20 01 00 59 00 …              LEVEL = 0x59 = 89%
```

连测 3 次均为 89%。

**踩到的坑（已写进设备包）：**

| 现象 | 原因 | 解法 |
|---|---|---|
| 发到 `if4` 只拿到固定 `0F 01 01 11` | `if4` 是 65 字节通道，等于命令发错地方 | 认准 **`if3` + 33 字节** |
| `if3` 写入成功但完全没回包 | **键盘休眠了**，dongle 转过去没人接 | 每 120ms 连发 3 次唤醒，再等最多 2.5 秒 |
| `0F 01 01` 看着像数据 | `0F+01+01 = 0x11` 正好是末字节，那是 NAK | 校验位不能当数据读 |

**额外收获：这套协议是同族的。** 同协议还覆盖 AJAZZ AK820 MAX / AK980 V2 / AK820 Pro、EPOMAKER 多款。**加新键盘多半只改 VID/PID**，不用重写实现。

> 顺带：`if4` 的 `0F 01 01` 曾经让我误以为读到了"17%"——这正是"校验位当数据"的典型陷阱。设备包里显式写了 `range: [0,100]` 和 `contains: ["20 01"]` 就是为了挡这种假阳性。

### 1.8 重力星球：协议已摸清，电量字段待判决

接收器 `3554:FA09`「2.4G Wireless Receiver」厂商标识 `CX`，是 **Compx 的通用模块**——AULA F75 / F99 Pro / X99 Pro 都在用同一个 VID:PID。所以它是一个ODM 方案，不是某个品牌独有。

**两个社区项目的结论都是"不支持"**：

| 项目 | 结论 |
|---|---|
| `harshvats17/f75-linux-manager` | 能用 `13 44 01 00` 读配置（读-改-回读校验），但 `battery` 只能被动监听、让用户按 Fn+B；实测只有普通键盘输入报告，**无厂商电量报告**；Fn+B 的电量显示由键盘固件本地处理 |
| `oneday5799/PeriTray` | F99 Pro / X99 Pro 列为"暂不支持：write 可达但设备不回复（500ms 超时）"——**他们发的是 SONiX 的 `20 01`，帧格式和长度都不对，所以设备当然不理** |

**我们的实测把协议摸清了。** 帧格式 20 字节：

```
[0]    0x13        Report ID
[1]    cmd         命令字
[2]    subcmd      子命令
[3]    seq         分片序号
[4..18] payload    15 字节
[19]   checksum    前面所有字节之和 & 0xFF
```

已确认的命令字：

| cmd | 作用 | 回包特征 |
|---|---|---|
| `0x44` | 读配置 | `13 44 0A seq …`，`[2]=0x0A` 表示共 10 个分片，`seq` 选择分片 |
| `0x04` | 写配置 | — |
| `0x09` | 调色板（37 帧） | — |
| `0x0A` | 保存到 flash | — |
| **`0x41`** | 未知读（大表） | `[2]=0x24` → 36 个分片 |
| **`0x42`** | 未知读 | `[2]=0x1B` → 27 个分片 |
| **`0x43`** | 未知读（含大量 FF） | `[2]=0x25` → 37 个分片 |
| **`0x49`** | 未知读 | `[2]=0x23` → 35 个分片 |
| **`0x4A`** | **未知读，最像电量** | `13 4A 01 00 02 64 01 …` → `0x64 = 100` |
| `0x05` / `0x07` | 未知读 | 内容稳定 |

**10 个配置分片里只有灯效参数**（`04 36 / 04 17 / 04 10` 这类亮度速度表），没有电量字段。

**当前唯一像电量的候选**：`0x4A` 回包 `02 64 01` —— `[5]=100`、`[6]=1`。

**已排除"亮度"**：把键盘亮度从 100 调到 25（该键盘亮度只有 0/25/50/75/100 五档），`[5]` 三次读取**均为 100，纹丝不动**。这是一次很干净的自然实验——不用插拔、不用抓包。

剩下两个候选，用同一逻辑即可判决：

| 候选 | 判决动作 | 判据 |
|---|---|---|
| **音量**（旋钮 0-100） | 转动音量旋钮 | `[5]` 跟着变 → 是音量，不是电量 |
| **电量** | 插上充电线 | `[5]`/`[6]` 跳变或翻转 → 是电量/充电状态 |

判决脚本（带时间轴提示，照着做即可）：`python tools/probe/probe_grava.py`

> 附带好消息：调亮度后重读配置，`effect_id` 已回到 `01` —— 之前扫描造成的灯效副作用被固件自己重写修正了。

**亮度字段已定位（2026-11-21）**：在配置分片 `seq4` 的**第 7 字节**，存的是 **0–4 档位而非百分比**（×25% 即得分比）。

| 亮度 | seq4 第 7 字节 |
|---|---|
| 100% | `0x04` |
| 25% | `0x01` |

这解释了该键盘"亮度只有 0/25/50/75/100 五档"的原因——固件里就是一个 5 档枚举，没有连续调光。

第 8 字节**不是**亮度：同一亮度档下它在 `0x00` 和 `0x10` 之间自行跳动（疑似速度/状态位），不能与第 7 字节混为一个 16 位值。

> 定位方法与踩过的坑：用 `find_brightness.py` 做 A/B/C 三次快照（A=25, B=100, C=25），A 与 C 一致才说明变量干净。第一次用十几分钟前的旧快照对比，中途灯效被改过，结论失真；第二次键盘休眠只读到 5/10 片。**差分对比的前提是"单一变量 + 完整采样"，缺一不可。**

**重要推论**：亮度字段的偏移与结构与 `donglover69/sonix-keyboard-studio` 记录的 SONiX 协议完全一致（分片 4、偏移 7 = 效果 1–6 的亮度）。**说明重力星球这台跑的也是同一套 SONiX/Compx 固件协议。** 而该协议族的公开实现（`f75-linux-manager`）在同一个 `3554:FA09` 接收器上得出"读不到电量，Fn+B 由键盘本地处理"的结论——这显著降低了重力星球能读电量的可能性。

**判决方法（待做）**：插上充电线看 `[5]` / `[6]` 是否跳变。脚本已备好：

```
python tools/probe/probe_grava.py -s 40
```

> ⚠️ **副作用警告**：命令字扫描时，`cmd=0x08` 意外触发了一次保存，导致配置里的 `effect_id` 从 `01` 变成 `0B`（灯效可能已改变）。恢复方式：用键盘上的灯效组合键切回，或由程序写回原配置（需写 flash）。**这也是"盲扫命令字"的真实代价——以后扫写命令必须更严格地隔离。**

**最终结论（2026-11-21）：该设备不提供电量，放弃。**

判决实验数据（`probe_grava.py`，42 秒，含插拔充电线）：

| 字段 | 全程表现 | 判读 |
|---|---|---|
| `[5]` | **恒为 100**，插线/拔线/按键均不变 | 不是实时电量 |
| `[6]` | `0x10` → `0x11` → `0x01` | 变换时机对不上插拔（8.2s 已变 `0x11`，20s 才插线）→ 不是充电标志 |

三条否决理由：

1. **不随充电变化** —— 电池读数在插电时至少该跳变或翻转状态位
2. **不随使用变化** —— 42 秒内精确恒定，真实电量读数不会这么"完美"
3. **协议同宗** —— 亮度字段位置/偏移/档位编码与 AULA F75 完全一致，同一套 ODM 固件；该固件在同一 `3554:FA09` 接收器上已被公开实现判定"读不到电量，Fn+B 由键盘本地处理"

另一条实测行为：**插上充电线期间（约 12 秒）厂商通道完全停止应答**，拔线后恢复——该通道与有线模式互斥。

结论已固化到 `device-packs/__unsupported.json`，程序遇到该 VID:PID 会直接标注"此设备不提供电量"，不再反复重试或报错。**v1 只支持 ATK 鼠标与狼蛛键盘两台设备。**

## 2. 核心问题一：电量数据从哪来

### 2.1 接收器在系统里长什么样

2.4G 接收器插上后是一个 **HID 复合设备**，通常包含 4 个接口：

```
接收器（一个物理设备，多个 HID 接口）
├── 标准键盘接口      usage_page 0x0001   ← 系统自带的键盘功能
├── 标准鼠标接口      usage_page 0x0001   ← 系统自带的鼠标功能
├── 消费者控制接口    usage_page 0x000C   ← 多媒体键
└── 厂商自定义接口    usage_page 0xFF00 ~ 0xFFFF   ← 电量、DPI、灯光都走这里
```

**电量只在第四个接口里。** 厂商驱动往这个接口写一段查询帧（Output Report），接收器从 Input Report 回一段数据，电量藏在其中某个字节。

所以每台设备的适配，本质是回答三个问题：

1. **认接口**：`vid` / `pid` / `usage_page` / 报文长度 / 报告 ID 是什么？
2. **发对帧**：厂商软件发出的那串十六进制是什么？要不要握手？要不要校验？
3. **取对字节**：回包从第几字节是电量？百分比还是电压？要不要换算？

### 2.2 五条取数路径（按优先级）

| 优先级 | 路径 | 说明 | 代价 |
|---|---|---|---|
| **① 最优** | **被动监听 Input Report** | 不少 dongle 会周期性主动上报电量，只需打开接口读，**一个字节都不用发** | 零风险、零副作用；但并非所有设备都主动推 |
| ② 主力 | **主动发送查询帧** | 抓包拿到厂商驱动的查询帧，我们自己复现 | 需要抓包；要保证只读、不发配置写入帧 |
| ③ 捷径 | **逆向 WebHID 网页驱动** | 品牌有网页版驱动时，直接读 JS 里的命令字节 | 仅 ATK 这类有网页驱动的适用；成本极低 |
| ④ 兜底 | **切蓝牙模式读标准 GATT** | 三模设备切 BT 后大概率有 `0x180F` 电池服务 | **牺牲 2.4G 低延迟与高回报率，鼠标不可接受**；键盘勉强可接受 |
| ⑤ 最后 | **UI 自动化抓驱动界面文本** | 读官方驱动窗口上的电量数字 | 脆弱、依赖界面版本与 DPI，不进主流程 |

**设计原则：优先被动，其次主动查询，且绝不写入。** 除了那条电量查询帧，不向设备发送任何配置写入——这个工具不该有能力改坏用户的设备设置。

### 2.3 抓包方法论（这是本项目的核心工序）

全程只需要：一台 Windows、设备、接收器、**厂商自己的驱动软件**。厂商软件的作用是"帮我们触发查询帧"，抓完就可以关掉。

**第一步：定位接口**

设备管理器 → 人体学输入设备 → 找到接收器条目（拔插一次看哪个消失）→ 属性 → 详细信息 → 硬件 ID：

```
HID\VID_373B&PID_1216&REV_0100&MI_02
     ^^^^^^^^ ^^^^^^^^            ^^^^^
       VID     PID            复合设备接口序号
```

**第二步：抓包（三种工具，按场景选）**

| 工具 | 优点 | 缺点 |
|---|---|---|
| **Wireshark + USBPcap** | 完整 USB 报文流，可保存、可过滤、可逐帧差分 | 需装 USBPcap 内核驱动（要管理员）；经 HUB/扩展坞时可能抓不到中断传输 |
| **Bus Hound** | 老牌，HID 抓取成功率高 | 界面古老，免费版限长度 |
| **API Monitor**（hook `HidD_GetFeature`/`HidD_SetFeature`） | **不需要驱动、不需要抓包**，直接看驱动调用 API 时传的 buffer | 只对走 hid.dll 的驱动有效；对直接走 WinUSB 的无效 |

抓包操作：打开厂商驱动 → 等它刷新一次电量 → 在驱动里切到电量页 / 切 DPI / 灯光 → 把设备关机再开机（初始化帧信息量最大）。过滤器用 `usb.idVendor == 0x373B`。

**第三步：在报文里找那一对帧**

- `URB_INTERRUPT out` → 主机发给接收器，**这是查询帧**
- `URB_INTERRUPT in` → 接收器回主机，**这是回包**
- 找 `HID Data` 字段，导出 hex

判断哪一对是"读电量"：

- **周期性**：驱动开着时每隔几秒稳定出现一对
- **定长**：每次长度一致，只有个别字节变化
- **差分**：电量从 A% 掉到 B% 时，逐字节对比，只有 1–2 个字节跟着变 → 就是它
- **对照数值**：驱动显示 87% 时，在回包里搜 `57`（87 的十六进制）；若是 0.1% 精度可能是 `66 03`（870）

**第四步：验证**

对着驱动显示的数字核一遍；再关机看回包（很多设备关机后会回一帧全 0，必须和"真的 0%"区分开）。

### 2.4 声明式设备包（关键架构决策）

**不把协议写进 C# 代码**，而是写成一个 JSON：

```jsonc
{
  "key": "atk-a9-plus",
  "name": "ATK 蜻蜓 A9 Plus",
  "type": "mouse",
  "transport": { "type": "hid" },
  "match": {
    "vid": "0x373B",
    "pid": "0x1216",
    "usage_page": "0xFF05",
    "min_in": 8,
    "min_out": 8
  },
  "read": {
    "query": ["08 7D 72 02 00 01 07 01"],   // 首字节是 Report ID，必须原样带上
    "checksum": { "mode": "none" },
    "attempts": 3,
    "listen_ms": 800,
    "reply": {
      "contains": ["7D 72"],
      "battery": { "byte": 7 },
      "range": [1, 100]
    }
  }
}
```

好处：

- 加新设备 = 加一个 JSON，不改代码、不发版
- 用户之间可以互相交换配置文件
- 固件升级导致偏移变了，改一行 JSON 就行
- 电量换算复杂度（电压→百分比、档位映射、0.1% 精度、位域提取）都能在配置里表达

字段能力（覆盖实际会遇到的复杂度）：

| 需求 | 表达方式 |
|---|---|
| 单字节百分比 | `{ "byte": 7 }` |
| 两字节小端、0.1% 精度 | `{ "byte": 7, "bytes": 2, "order": "little", "scale": 0.1 }` |
| 电压→百分比 | `{ "read_as": "voltage", "voltage_scale": 0.001, "voltage_min": 3.3, "voltage_max": 4.2 }` |
| 档位映射 | `{ "map": [[0,0],[1,25],[2,60],[3,100]] }` |
| 充电状态位 | `"charging": { "byte": 8, "mask": "0x01" }` |
| 关机假帧（回 0 但不是没电） | `"zero_is_off": true` |
| 需要先发唤醒帧 | `"pre": [...], "pre_delay_ms": 50` |
| 设备开机主动推送，无需查询 | `query` 留空，写 `"passive_ms": 1500` |
| 接收器是虚拟串口（CH340 等） | `"transport": { "type": "serial", "baud": 115200 }` |

### 2.5 参考实现（都是可借鉴的真实项目）

| 项目 | 价值 |
|---|---|
| `jiumo1436/open24g-batmon` | **配置驱动的 2.4G 电量读取方案，方法论文档极完整**（认接口→发帧→取字节→校验→换算→排查表全套）。它的配置 schema 可直接作为我们设备包格式的蓝本 |
| `yszyszysz233/2.4G-battery-viewer` | 纯 ctypes 实现，**已适配 ATK/VXE 鼠标（373B:1216）**，含"捕获报文 / 探测 Report ID / 手动标定"的调试台思路 |
| `Tan-TanZi/InphicBatteryTray` | 英菲克鼠标，20KB 单文件托盘工具；**演示了被动监听 Input Report 的做法**，以及"8 秒无上报则灰显、保留末次值"的离线处理 |
| `V-Conet/wukong-driver` | 京造 JZ M5，**从 WebHID 网页驱动逆向出本地协议**，完整展示了网页驱动这条路怎么走 |
| `renanleonel/windows-taskbar-battery` | 任务栏挂载 + 多源聚合的成熟参考（协议部分不适用，但 UI 与聚合层可借鉴） |

**建议动作**：先用 `open24g-batmon` 或 `2.4G-battery-viewer` 在你机器上实测一遍，确认 ATK 鼠标能读到数——这能在一天内验证整条链路成立，再决定自研范围。

## 3. 核心问题二：怎么"进"任务栏

### 3.1 现实约束

Windows 11 重写了任务栏（XAML），**移除了第三方工具栏（DeskBand）支持**，也没有公开的任务栏小组件 API：

- ❌ 不能注册"任务栏插件"让系统帮你放进去
- ❌ Win11 Widgets 第三方接入需 MSIX 打包 + 商店分发，且不是"任务栏底边"
- ✅ 唯一可靠形态：**自己建窗口，挂到任务栏上**

### 3.2 通用做法（TrafficMonitor / TaskbarMonitor 验证过）

```
FindWindow("Shell_TrayWnd")
  → 找子窗口 "TrayNotifyWnd"（通知区）的真实矩形
  → 创建 layered 子窗口
  → SetParent 到 Shell_TrayWnd
  → SetWindowPos 排到通知区左侧
  → UpdateLayeredWindow 逐像素 alpha 绘制文字
```

必须处理好的细节（都是别人踩过的坑）：

| 问题 | 处理 |
|---|---|
| GDI 直绘有灰底块 | 必须 `UpdateLayeredWindow` 逐像素 alpha，才能和 Mica/亚克力背景融合 |
| explorer 崩溃重启 | 监听 `TaskbarCreated` 注册消息 → 重建窗口 |
| 任务栏自动隐藏 | 跟随 `Shell_TrayWnd` 位置变化 |
| DPI 缩放 / 主题切换 | 监听 `WM_DPICHANGED` / `WM_SETTINGCHANGE`，重取字体与配色 |
| 触屏设备任务栏更高 | 用 `TrayNotifyWnd` 实际矩形，不要靠屏幕尺寸推算 |
| 游戏全屏被干扰 | 检测前台全屏窗口时自动隐藏 |
| 多显示器 | **v1 只支持主屏**，副屏留 v2 |

### 3.3 降级方案：托盘图标

把 "85%" 渲染进托盘图标（按实际像素尺寸绘制，不能靠缩放），右键弹面板看详情。

**v1 双形态并存**：托盘图标永远在（保底、零风险），任务栏条作为可选项。挂载失败自动降级。

## 4. 系统架构

```
┌────────── 采集层 ──────────┐
│  HidPolling (通用引擎)     │  读 device-packs/*.json，按配置发帧/收帧
│  SerialPolling             │  虚拟串口型 dongle
│  [预留] BleGatt            │  将来若加蓝牙设备
└────────────┬───────────────┘
             ▼
   ┌──────────────────────┐
   │   DeviceRegistry     │  按 vid:pid:serial 合并去重，绑定设备包
   └──────────┬───────────┘
              ▼
   ┌────────────────────────────────┐
   │   SamplingScheduler            │  被动优先；主动查询分源节奏；休眠退避
   └───────────────┬────────────────┘
                   ▼
         ┌──────────────────┐
         │   StateStore     │  last-known + 时间戳 + 新鲜度
         └────────┬─────────┘
                  ▼
   ┌──────────────┴──────────────┐
   ▼                             ▼
┌─────────────────┐      ┌─────────────────┐
│ TaskbarStrip    │      │ TrayIcon        │
│ layered 子窗口   │      │ 动态图标 + 菜单 │
└─────────────────┘      └─────────────────┘
                  ▼
         ┌──────────────────┐
         │  Notifier        │  低电 toast，带回弹抑制
         └──────────────────┘
```

**关键点：采集层只有一个通用引擎。** 不为每个品牌写一个 provider，而是"一个引擎 + N 份配置"。这是与 v0.1 最大的结构差异。

### 4.1 采样节奏

**查询帧会占用无线链路带宽。** 2.4G dongle 的 vendor 通道和键鼠数据共用同一条无线链路，查询太频繁会影响输入延迟——这对游戏鼠标是硬伤。

| 场景 | 间隔 |
|---|---|
| 被动监听（有上报就用） | 不主动发，纯读 |
| 主动查询（鼠标） | 60 s 起，游戏进行中暂停 |
| 主动查询（键盘） | 60 s |
| 设备休眠 | 不唤醒，保留末次读数并置灰 |
| 插拔 / 连接态变化 | 事件驱动即时采一次 |

### 4.2 统一数据模型

```jsonc
{
  "id": "hid:373b:1216",
  "name": "ATK 蜻蜓 A9 Plus",
  "kind": "mouse",
  "transport": "2.4g",
  "pack": "atk-a9-plus",
  "level": 84,
  "charging": false,
  "state": "connected",     // connected | sleeping | offline | unknown
  "confidence": "high",     // high=直接百分比 / medium=电压换算 / low=档位映射
  "updatedAt": "2026-11-21T19:20:00+08:00",
  "stale": false
}
```

## 5. 技术栈选型

| 方案 | 优势 | 代价 | 结论 |
|---|---|---|---|
| **A. C# / .NET 8 + WPF** | HID 用 HidSharp；串口用 `System.IO.Ports`；Win32 P/Invoke 直调；开发最快 | 常驻 40–80 MB | **推荐** |
| B. C++ / Win32 + Direct2D | 单文件 1–3 MB，内存 <10 MB | 开发慢 3–5 倍 | 在意体积再重写 |
| C. 纯 Python（ctypes） | 原型极快，适合调试台 | 打包体积大、常驻不优雅 | **只用来做协议调试台**，不做成品 |

依赖：`HidSharp`、`H.NotifyIcon.Wpf`、`System.Text.Json`、P/Invoke（`user32` / `setupapi` / `cfgmgr32`）。

**调试台建议用 Python 单独写**（`tools/probe`），因为它要试错、要频繁改，Python 最省事；成品用 C#。

## 6. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 设备关机后回全 0 帧 | 把"关机"误报成"电量 0%"并狂弹低电提醒 | `zero_is_off` 开关，默认关闭需实测确认；区分"真 0%"与"关机" |
| 与厂商驱动抢 HID 句柄 | 读不到，或导致驱动异常 | 共享模式打开（`FILE_SHARE_READ\|FILE_SHARE_WRITE`）；检测到驱动占用时提示 |
| 查询帧影响无线链路 | 游戏时输入延迟变差 | 被动优先；主动查询 60s 起；检测到游戏进程时暂停 |
| 误发配置写入帧 | 改坏用户设备设置 | **引擎只允许发送配置里声明的只读查询帧**，写入指令在 schema 层就禁掉 |
| 固件升级后协议偏移变化 | 读不到或读到错值 | 设备包版本化；读数超出 `range` 时标记为"不可信"而非硬显示 |
| 某些 dongle 不暴露厂商接口 | 该设备无解 | P0 先枚举确认；无解设备在 UI 里明确标注"此设备不提供电量" |
| 抓包需 USBPcap 管理员驱动 | 普通用户装不上 | **只在开发期需要**，运行期不需要任何驱动/管理员权限 |
| 杀软误报 | 用户不敢用 | 不装驱动、不挂钩子、不注入；只做 HID 读写 + 窗口操作 |

## 7. 分阶段路线

### P0 · 协议验证（最先做，2–3 天）

**目标：证明四台设备能不能读到，并产出第一批设备包。**

1. ✅ **拿 ATK 鼠标开刀** —— **已完成**。直接用社区已验证的帧在真机上打通，产出 `device-packs/atk-a9-plus.json`，见 §1.1
2. **做协议调试台通用化**（Python，`tools/probe`）：目前 `probe_atk.py` 只覆盖 ATK 一条硬编码路径，需要泛化成「读设备包 JSON 发帧 + 逐字节差分」
   - 枚举所有 HID 接口，打印 `vid/pid/usage_page/report id/报文长度/描述符`
   - 发任意十六进制帧，打印回包 hex
   - 逐字节差分（连按两次，高亮变化的字节）
   - 按设备包配置实时解析并显示结果
3. **抓狼蛛 F108 Pro**：装官方驱动 → USBPcap 抓包 → 找出电量查询帧
4. **抓重力星球 / 耳机**：同上

**验收标准**：至少 3 台设备能在调试台里稳定读到电量，且与官方驱动显示一致。

### P1 · 引擎 + 托盘（MVP）
- 通用 HID 采集引擎（读设备包 JSON）+ 串口通道
- DeviceRegistry、SamplingScheduler、StateStore
- 托盘图标动态绘制，右键面板列设备
- 低电 toast（带回弹抑制）

### P2 · 任务栏条
- layered 窗口挂载、逐像素 alpha 文字
- explorer 重启自愈、全屏隐藏、主题/DPI 跟随
- 显示策略：最紧急优先 / 轮播 / 全部并排

### P3 · 打磨
- 设备包管理界面（导入/导出/编辑，带"测试读取"）
- 开机自启（计划任务，避免 UAC）
- 设备别名、阈值、轮询间隔配置
